## 1. Basics & Type System

### ✅ Type Annotations & Inference

**Type annotation** — explicitly telling TypeScript the type of a variable.

```ts
let name: string = "Atik";
let age: number = 30;
let active: boolean = true;
```

**Type inference** — TypeScript figures out the type automatically from the assigned value. Prefer this when the type is obvious.

```ts
let name = "Atik";   // inferred as string
let age = 30;         // inferred as number
let active = true;    // inferred as boolean
```

Annotate only when inference isn't possible or when the inferred type is too wide.

```ts
// Needs annotation — no initial value to infer from
let input: string;
input = "hello";

// Needs annotation — inferred as number[], but you want a specific shape
function getUser(): { name: string; age: number } {
  return { name: "Atik", age: 30 };
}
```

#### `typeof` as a type operator

Capture the type of any value at the type level — different from the JS runtime `typeof`:

```ts
const config = { port: 3000, host: "localhost" };
type Config = typeof config; // { port: number; host: string }

function greet(name: string) { return `Hello, ${name}`; }
type GreetFn = typeof greet; // (name: string) => string
```

Pairs naturally with `ReturnType<>` and `Parameters<>` (covered in Utility Types).


### ✅ Primitive Types

TypeScript's primitive types map directly to JavaScript primitives.

```ts
let str: string = "hello";
let num: number = 42;          // int, float, hex, binary all use number
let bool: boolean = true;
let big: bigint = 100n;        // TS 3.2+
let sym: symbol = Symbol("id");

// Special
let nothing: null = null;
let missing: undefined = undefined;
```

#### Arrays & Tuples

```ts
// Arrays
let nums: number[] = [1, 2, 3];
let strs: Array<string> = ["a", "b"]; // generic syntax — fully interchangeable with T[]

// Tuples — fixed length, fixed types per position
let point: [number, number] = [10, 20];
let entry: [string, number] = ["age", 30];

// Named tuple elements (TS 4.0+)
let range: [start: number, end: number] = [1, 100];

// Rest elements — variable-length tail
type StringThenNumbers = [string, ...number[]];

// Optional elements
type MaybeAge = [string, number?];
```

#### Object types

```ts
let user: { name: string; age: number } = { name: "Atik", age: 30 };

// Optional property
let config: { port: number; host?: string } = { port: 3000 };

// readonly properties — prevents mutation at the type level
type Point = { readonly x: number; readonly y: number };
const nums: readonly number[] = [1, 2, 3]; // nums.push(4) → Error
```

#### `object`, `{}`, and `Object`

A common source of confusion — these three are not the same:

```ts
let a: object  = {};       // any non-primitive (no string, number, boolean, etc.)
let b: {}      = "hello";  // anything that isn't null or undefined (NOT "empty object")
let c: Object  = 42;       // same as {} in practice — avoid, prefer object or {}
```

| Type | Accepts primitives | Accepts null/undefined |
|------|-------------------|----------------------|
| `object` | ❌ | ❌ |
| `{}` | ✅ | ❌ |
| `Object` | ✅ | ❌ |

In practice: use `object` when you mean "not a primitive", use `unknown` when you mean "anything".


### ✅ `any`, `unknown`, `never`, `void`

#### `any`

Opts out of type checking entirely — TypeScript treats it like plain JavaScript.

```ts
let data: any = "hello";
data = 42;           // ok
data.foo.bar();      // ok — no error, but dangerous at runtime
```

Avoid `any` in modern TypeScript. It silences errors without solving them.

#### `unknown`

The type-safe alternative to `any`. You can assign anything to it, but you must **narrow the type** before using it.

```ts
let input: unknown = getUserInput();

// Must check before use
if (typeof input === "string") {
  console.log(input.toUpperCase()); // safe
}

// Without check — error
input.toUpperCase(); // Error: Object is of type 'unknown'
```

**`unknown` vs `any`:**

| | `any` | `unknown` |
|---|---|---|
| Assign anything to it | ✅ | ✅ |
| Use without type check | ✅ | ❌ |
| Type-safe | ❌ | ✅ |
| Use for | Legacy escape hatch | External data, API responses |

#### `never`

Represents a value that **never occurs** — the bottom type. Used for:

1. Functions that never return (throw or infinite loop):

```ts
function fail(msg: string): never {
  throw new Error(msg);
}

function infinite(): never {
  while (true) {}
}
```

2. Exhaustiveness checking in switch statements:

```ts
type Shape = "circle" | "square";

function area(shape: Shape): number {
  switch (shape) {
    case "circle": return Math.PI;
    case "square": return 1;
    default:
      const _check: never = shape; // Error if a new case is added and not handled
      return _check;
  }
}
```

#### `void`

Used as the return type of functions that don't return a meaningful value.

```ts
function log(msg: string): void {
  console.log(msg);
  // no return
}
```

`void` vs `never`: `void` functions return `undefined` implicitly — they just finish. `never` functions never finish at all.


### ✅ `null` & `undefined` — `strictNullChecks`

By default (`strictNullChecks: false`), `null` and `undefined` are assignable to every type — a common source of runtime bugs.

With `strictNullChecks: true` (recommended — also enabled by `strict: true`):

```ts
let name: string = null;      // Error — null not assignable to string
let age: number = undefined;  // Error
```

To allow `null` or `undefined`, use a union:

```ts
let name: string | null = null;       // ok
let age: number | undefined = undefined; // ok
```

#### Non-null assertion `!`

Tells TypeScript "I know this isn't null or undefined" — use only when you're certain.

```ts
const input = document.getElementById("name"); // HTMLElement | null

input!.focus(); // asserts: input is not null
```


### ✅ Type Assertions

Tell TypeScript to treat a value as a specific type. Does **not** change the runtime value — compile-time only.

```ts
const input = document.getElementById("name") as HTMLInputElement;
input.value; // ok — TS now knows it's an input element

// Angle bracket syntax (not allowed in JSX)
const input2 = <HTMLInputElement>document.getElementById("name");
```

#### `as const`

Narrows a value to its most specific literal type and makes it `readonly`.

```ts
// On a top-level const primitive, the literal type is already inferred:
let direction = "left";    // inferred: string (let widens)
const direction2 = "left"; // inferred: "left" (const already narrows — as const adds nothing here)

// as const is most valuable on objects — properties widen to string even in const objects:
const obj  = { direction: "left" };           // { direction: string }
const obj2 = { direction: "left" } as const;  // { readonly direction: "left" }

const config = { port: 3000, host: "localhost" } as const;
// { readonly port: 3000; readonly host: "localhost" }
```

`as const` is essential when object/array values should never widen — it adds both the literal type and `readonly`.


### ✅ Literal Types

A literal type is an exact value used as a type.

```ts
let direction: "left" | "right" | "up" | "down";
direction = "left";  // ok
direction = "jump";  // Error

let statusCode: 200 | 400 | 404 | 500;
statusCode = 200;    // ok
statusCode = 999;    // Error
```

#### Template literal types (TS 4.1+)

```ts
type EventName = `on${Capitalize<string>}`;
// matches: "onClick", "onChange", "onSubmit" ...

type Direction = "top" | "bottom";
type Side = "left" | "right";
type Position = `${Direction}-${Side}`;
// "top-left" | "top-right" | "bottom-left" | "bottom-right"
```


### ✅ Type Widening & Narrowing (concept)

**Widening** — TypeScript generalises a literal to a broader type when it might change:

```ts
let x = "left";        // string — let can be reassigned, so TS widens
const y = "left";      // "left" — const can't change, TS keeps the literal
const obj = { d: "left" }; // { d: string } — object properties can be mutated, so TS widens
```

**Narrowing** — TypeScript refines a broad type to a specific one inside a conditional:

```ts
function process(val: string | number) {
  if (typeof val === "string") {
    val.toUpperCase(); // val is string here
  } else {
    val.toFixed(2);    // val is number here
  }
}
```

`as const` prevents widening. Type guards (`typeof`, `instanceof`, `in`, custom `is`) perform narrowing. Both concepts underpin most advanced TypeScript patterns.


### ✅ `satisfies` Operator (TS 4.9+)

Validates that a value matches a type **while preserving the inferred literal type**. Safer than a type annotation or `as` assertion.

```ts
type Colors = "red" | "green" | "blue";
type RGB = [number, number, number];

const palette = {
  red: [255, 0, 0],
  green: "#00ff00",
  blue: [0, 0, 255],
} satisfies Record<Colors, RGB | string>;

// TypeScript validates against Record<Colors, RGB | string>
// BUT preserves the actual inferred types:
palette.red;    // inferred as [number, number, number] — not RGB | string
palette.green;  // inferred as string — not RGB | string
palette.green.toUpperCase(); // ok — TS knows it's a string
palette.red.map(x => x);    // ok — TS knows it's an array
```

#### `satisfies` vs type annotation vs `as`

```ts
// Type annotation — validates but WIDENS the type
const p1: Record<Colors, RGB | string> = { red: [255,0,0], green: "#00ff00", blue: [0,0,255] };
p1.red; // RGB | string — lost the specific type

// as assertion — DOES NOT validate, just asserts
const p2 = { red: [255,0,0] } as Record<Colors, RGB | string>;
// No error even though green and blue are missing!

// satisfies — validates AND preserves
const p3 = { red: [255,0,0], green: "#00ff00", blue: [0,0,255] } satisfies Record<Colors, RGB | string>;
p3.red; // [number, number, number] ✅
```

| | Validates against type | Preserves literal type |
|---|---|---|
| Type annotation | ✅ | ❌ (widens) |
| `as` assertion | ❌ | ✅ |
| `satisfies` | ✅ | ✅ |
