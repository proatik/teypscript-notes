## 6. Classes

### ✅ Class Basics in TypeScript

TypeScript classes build on JavaScript classes and add type checking for properties, methods, and access control.

```ts title="User.ts"
class User {
  name: string;
  age: number;

  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
  }

  greet(): string {
    return `Hi, I'm ${this.name}`;
  }
}
```

```ts title="index.ts"
const user = new User("Atik", 30);
console.log(user.greet()); // "Hi, I'm Atik"
```


### ✅ Access Modifiers

Control where class members can be accessed.

| Modifier | Accessible from |
|----------|----------------|
| `public` | Anywhere (default) |
| `private` | Inside the class only |
| `protected` | Inside the class and subclasses |

```ts title="BankAccount.ts"
class BankAccount {
  public owner: string;
  private balance: number;
  protected accountType: string;

  constructor(owner: string, balance: number) {
    this.owner = owner;
    this.balance = balance;
    this.accountType = "checking";
  }

  public getBalance(): number {
    return this.balance; // ok — inside class
  }

  private validate(): boolean {
    return this.balance >= 0;
  }
}
```

```ts title="index.ts"
const account = new BankAccount("Atik", 1000);
account.owner;         // ok — public
account.balance;       // Error — private
account.getBalance();  // ok — public method
```

#### `private` vs `#` (ECMAScript private fields)

TypeScript `private` is compile-time only — the property still exists on the compiled object, but the type checker blocks access from outside the class. `#` is a JavaScript private field — enforced at runtime by the engine itself.

```ts title="Foo.ts"
class Foo {
  private tsPrivate = 1;   // compile-time only
  #jsPrivate = 2;           // runtime enforced
}
```

```ts title="index.ts"
const foo = new Foo();
(foo as any).tsPrivate; // accessible at runtime — no real protection
foo.#jsPrivate;         // SyntaxError — truly private
```

Prefer `#` for genuine runtime privacy.


### ✅ `readonly`

Prevents a property from being reassigned after construction.

```ts title="Point.ts"
class Point {
  readonly x: number;
  readonly y: number;

  constructor(x: number, y: number) {
    this.x = x; // ok in constructor
    this.y = y;
  }
}
```

```ts title="index.ts"
const p = new Point(1, 2);
p.x = 10; // Error — cannot assign to 'x' because it is a read-only property
```

Can be combined with access modifiers:

```ts title="Config.ts"
class Config {
  public readonly version = "1.0.0";
  private readonly secret: string;

  constructor(secret: string) {
    this.secret = secret;
  }
}
```


### ✅ Parameter Properties

Shorthand that **declares and initialises** class fields directly in the constructor signature.

**Without parameter properties:**

```ts title="User.ts"
class User {
  name: string;
  age: number;

  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
  }
}
```

**With parameter properties — same result:**

```ts title="User.ts"
class User {
  constructor(
    public name: string,
    public age: number,
    private readonly id: string,
  ) {}
}
```

Any access modifier (`public`, `private`, `protected`) or `readonly` in front of a constructor parameter creates a property automatically. `readonly` alone (without an access modifier) also works — it creates a `public readonly` property.


### ✅ `abstract` Classes

An abstract class cannot be instantiated directly — it exists to be extended. It can contain both implemented methods and **abstract methods** that subclasses must implement.

```ts title="Shape.ts"
abstract class Shape {
  abstract area(): number; // no implementation — subclass must provide

  describe(): string {     // concrete method — shared by all subclasses
    return `This shape has area ${this.area()}`;
  }
}
```

```ts title="Circle.ts"
class Circle extends Shape {
  constructor(private radius: number) { super(); }

  area(): number {
    return Math.PI * this.radius ** 2;
  }
}
```

```ts title="Square.ts"
class Square extends Shape {
  constructor(private side: number) { super(); }

  area(): number {
    return this.side ** 2;
  }
}
```

```ts title="index.ts"
const s = new Shape();   // Error — cannot instantiate abstract class
const c = new Circle(5); // ok
console.log(c.describe()); // uses inherited describe()
```


### ✅ `implements` vs `extends`

#### `extends` — inheritance

A subclass **inherits** properties and methods from the parent class and can override them.

```ts title="Animal.ts"
class Animal {
  constructor(public name: string) {}
  move(): void { console.log(`${this.name} moves`); }
}
```

```ts title="Dog.ts"
class Dog extends Animal {
  bark(): void { console.log("woof"); }
}
```

```ts title="index.ts"
const dog = new Dog("Rex");
dog.move(); // inherited
dog.bark(); // own method
```

#### `implements` — contract checking

A class declares that it satisfies an interface (or type alias). No inheritance — you write the implementation yourself.

```ts title="Serializable.ts"
interface Serializable {
  serialize(): string;
}
```

```ts title="Loggable.ts"
interface Loggable {
  log(): void;
}
```

```ts title="User.ts"
class User implements Serializable, Loggable {
  constructor(public name: string) {}

  serialize(): string {
    return JSON.stringify({ name: this.name });
  }

  log(): void {
    console.log(this.name);
  }
}
```

#### Key difference

| | `extends` | `implements` |
|---|---|---|
| Inherits implementation | ✅ | ❌ |
| Must write methods | Only overrides | All |
| Can use multiple | ❌ (one class) | ✅ (multiple interfaces) |
| Works with | Classes | Interfaces, types, classes |

A class can do both:

```ts title="Admin.ts"
class Admin extends User implements Serializable {
  serialize(): string {
    return JSON.stringify({ name: this.name, role: "admin" });
  }
}
```


### ✅ Getters & Setters

```ts title="Temperature.ts"
class Temperature {
  private _celsius: number;

  constructor(celsius: number) {
    this._celsius = celsius;
  }

  get fahrenheit(): number {
    return this._celsius * 9/5 + 32;
  }

  set celsius(value: number) {
    if (value < -273.15) throw new RangeError("Below absolute zero");
    this._celsius = value;
  }

  get celsius(): number {
    return this._celsius;
  }
}
```

```ts title="index.ts"
const t = new Temperature(100);
console.log(t.fahrenheit); // 212
t.celsius = -300;          // throws RangeError
```


### ✅ Decorators

A decorator is a function that runs against a class, method, property, or parameter at definition time — used to attach behaviour or metadata without changing the class body itself. TypeScript supports **two, incompatible** decorator systems.

#### Legacy decorators (`experimentalDecorators`)

The original TypeScript decorator implementation, based on an early (stage-2-ish) TC39 proposal. Still the style used by **Angular, NestJS, and TypeORM** today. Requires `"experimentalDecorators": true` in `tsconfig.json`.

```ts title="tsconfig.json"
{ "compilerOptions": { "experimentalDecorators": true, "emitDecoratorMetadata": true } }
```

```ts title="index.ts"
function LogClass(constructor: Function) {
  console.log(`Class: ${constructor.name}`);
}

function LogMethod(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const original = descriptor.value;
  descriptor.value = function (...args: any[]) {
    console.log(`Calling ${propertyKey}`);
    return original.apply(this, args);
  };
}

@LogClass
class Service {
  @LogMethod
  doWork(x: number) {
    return x * 2;
  }
}
```

#### Native decorators (TC39 Stage-3, TS 5.0+)

Shipped in TypeScript 5.0, based on the decorators proposal that's now standardized JavaScript syntax — no compiler flag needed, and it works even under `isolatedModules`/`erasableSyntaxOnly`-style pipelines since it's real JS, not a TS-only transform. The signature is different: decorators receive a `context` object instead of a target/key/descriptor triple.

```ts title="index.ts"
function logged<This, Args extends any[], Return>(
  target: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Return>
) {
  const methodName = String(context.name);
  return function (this: This, ...args: Args): Return {
    console.log(`Calling ${methodName}`);
    return target.call(this, ...args);
  };
}

class Service {
  @logged
  doWork(x: number) {
    return x * 2;
  }
}
```

**The two styles don't mix.** A decorator written for one system (target/key/descriptor) is not compatible with the other (target/context) — you can't apply a legacy-style decorator under native decorator semantics or vice versa. Pick one per project; `experimentalDecorators: true` forces every decorator in that project to use the legacy shape.

#### The `emitDecoratorMetadata` / `useDefineForClassFields` trap

This is what trips people up when migrating an older (Angular/NestJS/TypeORM-style) codebase to a newer `target`. Legacy accessor-style decorators (MobX's `@observable`, TypeORM's tracked columns, etc.) commonly install a getter/setter pair on the **prototype**. Modern targets (`ES2022`+) default `useDefineForClassFields` to `true`, which compiles class field initializers (`count = 0;`) using `[[Define]]` semantics — this creates a plain **own property** on the instance that silently shadows the prototype accessor, so the decorator's getter/setter never fires again:

```ts title="index.ts"
function tracked(target: any, key: string) {
  Object.defineProperty(target, key, {
    get() { return this[`_${key}`]; },
    set(v) { console.log(`set ${key}`); this[`_${key}`] = v; },
  });
}

class Widget {
  @tracked
  count = 0; // class field with a default value
}

const w = new Widget();
w.count = 5; // useDefineForClassFields: true → no "set count" log, decorator bypassed
             // useDefineForClassFields: false → logs "set count" as expected
```

Compiling and running this confirms the difference: with `useDefineForClassFields: true` the `tracked` setter never runs at all (the field becomes an own data property that shadows it), while with `false` every assignment goes through the setter as intended. If a legacy-decorator-based library (TypeORM, older MobX) starts silently losing reactivity or metadata after bumping `target` to `ES2022`+, this interplay is usually why — see the tsconfig & Strict Mode chapter for `target`/`useDefineForClassFields` details, and set `useDefineForClassFields: false` (or keep `target` at `ES2021` or below) to restore the old behaviour.
