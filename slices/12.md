## 12. tsconfig & Strict Mode

### ✅ What is `tsconfig.json`

The `tsconfig.json` file configures the TypeScript compiler — what files to include, which JavaScript version to target, and how strict the type checking should be.

```json title="tsconfig.json"
{
  "compilerOptions": { },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
```

Run `npx tsc --init` to generate a commented `tsconfig.json` with all options.


### ✅ `strict` & Strict Mode

`"strict": true` is a **single flag that enables a bundle of strict checks** at once (8 as of TS 4.4, 9 with TS 5.6+). It is the most important setting in any modern TypeScript project.

```json title="tsconfig.json"
{
  "compilerOptions": {
    "strict": true
  }
}
```

#### What `strict: true` enables

| Option | What it checks |
|--------|---------------|
| `noImplicitAny` | Error when a variable is implicitly typed as `any` |
| `strictNullChecks` | `null` and `undefined` are not assignable to other types |
| `strictFunctionTypes` | Stricter checking of function parameter types (contravariance) |
| `strictPropertyInitialization` | Class properties must be assigned in the constructor |
| `noImplicitThis` | Error when `this` has an implicit `any` type |
| `alwaysStrict` | Emits `"use strict"` in all output files |
| `strictBindCallApply` | Type-checks arguments of `.bind()`, `.call()`, `.apply()` |
| `useUnknownInCatchVariables` | Catch clause variables are `unknown`, not `any` |
| `strictBuiltinIteratorReturn` | Built-in iterator `.return()` is typed `undefined` not `any` (TS 5.6+) |

```ts title="index.ts"
// strictNullChecks: true
const input = document.getElementById("name"); // HTMLElement | null
input.focus(); // Error — input might be null

// noImplicitAny: true
function process(x) {} // Error — x has implicit any type

// useUnknownInCatchVariables: true
try {}
catch (err) {
  err.message; // Error — err is unknown, not any
  if (err instanceof Error) {
    err.message; // ok — narrowed to Error
  }
}
```

**Always use `strict: true`** in new projects. There is no good reason not to.

#### Gotcha: `strictFunctionTypes` doesn't protect method syntax

`strictFunctionTypes` only makes function **parameters** checked contravariantly (a subtype's method can't narrow a param type) — but this protection quietly does not apply to methods written with shorthand syntax on an interface or type. Shorthand methods are still checked **bivariantly** (loosely) for backward-compatibility with common OOP override patterns, even with `strict: true` on. A function-typed **property** with the same signature gets the full contravariant check:

```ts title="index.ts"
class Animal { name = "animal"; }
class Dog extends Animal { breed = "dog"; }

// Method shorthand — checked BIVARIANTLY, even under strictFunctionTypes
interface AnimalHandlerMethod {
  handle(a: Animal): void;
}
class DogHandlerMethod implements AnimalHandlerMethod {
  handle(a: Dog): void { console.log(a.breed); } // unsound, but no error
}

// Function-typed property — checked CONTRAVARIANTLY
interface AnimalHandlerProp {
  handle: (a: Animal) => void;
}
class DogHandlerProp implements AnimalHandlerProp {
  handle = (a: Dog): void => { console.log(a.breed); };
  // Error TS2416: Type '(a: Dog) => void' is not assignable to type '(a: Animal) => void'
}
```

Both interfaces look almost identical, but only the property form catches the unsound override. This is a known, intentional trade-off in the checker (see the Type vs Interface chapter for where method syntax is first introduced) — don't assume `strict: true` alone makes interface methods as safe as function-typed properties.


### ✅ `target` & `module`

#### `target`

Which JavaScript version to compile to.

```json title="tsconfig.json"
{ "target": "ES2022" }
```

| Target | Use when |
|--------|---------|
| `ES5` | Legacy browser support |
| `ES2017` | Older Node.js |
| `ES2020` | Modern browsers / Node.js 14+ |
| `ES2022` | Node.js 16+ / modern evergreen browsers (recommended) |
| `ESNext` | Latest features, requires up-to-date runtime |

#### `module`

What module format to emit.

```json title="tsconfig.json"
{ "module": "nodenext" }
```

| Module | Use when |
|--------|---------|
| `commonjs` | Node.js with `require()` (legacy) |
| `es2020` / `es2022` | Browser bundles (Webpack, Rollup) |
| `nodenext` | Node.js with native ESM (`"type": "module"`) |
| `preserve` | TS 5.4+ — keeps import/export syntax as-is for bundlers |
| `bundler` | Vite, esbuild, SWC — bundler handles module resolution |

#### `moduleResolution`

How TypeScript finds module files. Should match `module`:

| `module` | `moduleResolution` |
|----------|-------------------|
| `commonjs` | `node` |
| `nodenext` | `nodenext` |
| `bundler` | `bundler` |


### ✅ Key Compiler Options

```json title="tsconfig.json"
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true,
    "outDir": "./dist",
    "rootDir": "./src",
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,
    "verbatimModuleSyntax": true
  }
}
```

| Option | Purpose |
|--------|---------|
| `outDir` | Where compiled JS files go |
| `rootDir` | Root of source files (preserves directory structure) |
| `declaration` | Generate `.d.ts` files |
| `declarationMap` | Generate `.d.ts.map` for source navigation |
| `sourceMap` | Generate `.js.map` for debugging |
| `esModuleInterop` | Allows `import x from "module"` for CommonJS packages |
| `skipLibCheck` | Skip type checking of `.d.ts` files in `node_modules` (speeds up compile) |
| `forceConsistentCasingInFileNames` | Prevents import casing bugs on case-sensitive filesystems |
| `resolveJsonModule` | Allow importing `.json` files |
| `verbatimModuleSyntax` | Enforce explicit `import type` for type-only imports (TS 5.0+) |

**Decorator-related flags:** `experimentalDecorators` and `emitDecoratorMetadata` opt into the legacy decorator system (Angular/NestJS/TypeORM style); native TC39 decorators (TS 5.0+) need neither. `useDefineForClassFields` (defaults to `true` for `target: ES2022`+) can silently break legacy accessor-style decorators — see the Decorators section in the Classes chapter for the compiling example and why.


### ✅ Beyond `strict` — Additional Checks

These are not included in `strict: true` but are worth enabling in production:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "noImplicitReturns": true
  }
}
```

| Option | What it catches |
|--------|----------------|
| `noUncheckedIndexedAccess` | `arr[0]` returns `T \| undefined` — forces null check |
| `exactOptionalPropertyTypes` | Optional `?` props cannot be set to `undefined` explicitly |
| `noImplicitOverride` | Subclass methods must use `override` keyword |
| `noFallthroughCasesInSwitch` | Error on switch cases that fall through without `break` |
| `noImplicitReturns` | All code paths in a function must return a value |

```ts title="index.ts"
// noUncheckedIndexedAccess: true
const arr = [1, 2, 3];
const first = arr[0];          // number | undefined
const safe = arr[0] ?? 0;      // number — forced to handle undefined

// exactOptionalPropertyTypes: true
interface Config { port?: number }
const c: Config = { port: undefined }; // Error — cannot set optional to undefined
```


### ✅ Path Aliases

Avoid long relative imports with `baseUrl` and `paths`:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"],
      "@components/*": ["src/components/*"],
      "@utils/*": ["src/utils/*"]
    }
  }
}
```

```ts title="index.ts"
// Without alias
import { Button } from "../../../components/Button";

// With alias
import { Button } from "@components/Button";
```

**Note:** `paths` is TypeScript-only — your bundler (Vite, Webpack) also needs matching alias config.


### ✅ Project References

Split a large TypeScript project into smaller sub-projects that can be compiled independently and in parallel.

```json title="tsconfig.json"
{
  "references": [
    { "path": "./packages/core" },
    { "path": "./packages/ui" },
    { "path": "./packages/api" }
  ]
}
```

```json title="packages/core/tsconfig.json"
{
  "compilerOptions": {
    "composite": true,   // required for referenced projects
    "outDir": "./dist"
  }
}
```

Build with `tsc --build` (or `tsc -b`) — TypeScript only recompiles packages that have changed.

**Benefits:** Faster builds in monorepos, enforces clear package boundaries, enables parallel compilation.
