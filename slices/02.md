## 2. Type vs Interface

### ✅ `type` Aliases

A `type` alias gives a name to any type — primitives, unions, intersections, tuples, objects, and more.

```ts title="index.ts"
type ID = string | number;
type Point = { x: number; y: number };
type Callback = (event: MouseEvent) => void;
type Pair<T> = [T, T];
```

`type` can express anything — it's the most flexible option.


### ✅ `interface`

An `interface` describes the shape of an **object** (or class). It looks similar to an object `type` but has unique capabilities.

```ts title="User.ts"
interface User {
  name: string;
  age: number;
  greet(): void;
}
```

**Gotcha:** method-shorthand syntax like `greet(): void` above is checked **bivariantly** for parameter types — more loosely than the equivalent function-typed property `greet: () => void`, even with `strictFunctionTypes` on. See the `strictFunctionTypes` callout in the tsconfig & Strict Mode chapter for a compiling example of the difference.


### ✅ Key Differences

| Feature | `type` | `interface` |
|---------|--------|-------------|
| Objects | ✅ | ✅ |
| Primitives / unions / tuples | ✅ | ❌ |
| Declaration merging | ❌ | ✅ |
| `extends` keyword | via `&` intersection | `extends` keyword |
| `implements` in classes | ✅ | ✅ |
| Computed / mapped types | ✅ | ❌ |
| Can be generic | ✅ | ✅ |

The most important practical difference: **declaration merging**.

**Error message quality:** the common claim that `type` aliases generally expand inline in diagnostics while `interface` shows by name is broader than reality. Verified across alias kinds: plain object, union, and mapped-type aliases all display by their declared name in error messages, just like interfaces do (a mapped type shows as its generic form, e.g. `ReadonlyShape<Point>`, not fully expanded). **Conditional types are the real exception** — the checker has to evaluate a conditional type to know its resulting shape, so a `type` alias built on one resolves to its final expanded form (e.g. `string`) in diagnostics instead of keeping the alias name. So narrow the rule of thumb: type aliases built on conditional types are the ones most likely to lose their name and expand inline; plain object, union, and mapped-type aliases usually still display by name. This is a tooling/readability nuance, not a difference in type safety.


### ✅ Declaration Merging

Declaring an `interface` with the same name **twice merges** the two declarations into one. This is impossible with `type`.

```ts title="Window.ts"
interface Window {
  title: string;
}

interface Window {
  theme: "dark" | "light";
}

// Window is now: { title: string; theme: "dark" | "light" }
const w: Window = { title: "App", theme: "dark" }; // ok
```

Declaration merging is essential when **augmenting third-party types** (e.g. adding properties to `Express.Request` or the global `Window`) — see Module Augmentation in the Modules chapter for the real-world `declare global` version of this pattern.

```ts title="index.ts"
// Cannot do this with type
type Window = { title: string };
type Window = { theme: string }; // Error: Duplicate identifier 'Window'
```

**Caveat:** if two merged declarations define the same property with incompatible types, TypeScript errors at the second declaration:

```ts title="Foo.ts"
interface Foo { bar: string; }
interface Foo { bar: number; } // Error: Subsequent property declarations must have the same type
```

Method signatures with different parameter types are the exception — they merge as overloads.


### ✅ Extending & Implementing

#### Extending an interface

```ts title="Animal.ts"
interface Animal {
  name: string;
}
```

```ts title="Dog.ts"
interface Dog extends Animal {
  breed: string;
}
```

```ts title="index.ts"
const dog: Dog = { name: "Rex", breed: "Labrador" };
```

An interface can extend **multiple** interfaces at once:

```ts title="A.ts"
interface A { a: string }
```

```ts title="B.ts"
interface B { b: number }
```

```ts title="C.ts"
interface C extends A, B { c: boolean } // valid
```

#### Extending a type (via intersection)

```ts title="index.ts"
type Animal = { name: string };
type Dog = Animal & { breed: string };

const dog: Dog = { name: "Rex", breed: "Labrador" };
```

#### Interface extending a type

```ts title="User.ts"
type Named = { name: string };

interface User extends Named {
  age: number;
}
```

**Caveat:** an interface can only extend a `type` alias that resolves to an object type (or intersection of object types) with statically known members. A `type` alias for a union, primitive, or tuple cannot be extended this way:

```ts title="index.ts"
type ID = string | number;

interface Wrong extends ID {} // Error — an interface can only extend an object type
```

#### Type intersecting an interface

```ts title="Named.ts"
interface Named { name: string }
type User = Named & { age: number };
```

Both can extend/intersect each other freely, as long as the `type` side is an object shape.

#### `implements` in classes

A class can `implement` both an `interface` and a `type` (as long as the type is an object shape).

```ts title="Printable.ts"
interface Printable {
  print(): void;
}
```

```ts title="Serializable.ts"
type Serializable = {
  serialize(): string;
};
```

```ts title="Document.ts"
class Document implements Printable, Serializable {
  print() { console.log("printing"); }
  serialize() { return "{}"; }
}
```

**Union type trap:** a class cannot implement a union type — even if every member is an object shape:

```ts title="Foo.ts"
type AB = { a: string } | { b: number };
class Foo implements AB {} // Error: A class can only implement an object type or intersection
```

Use an intersection (`&`) or separate interfaces instead.


### ✅ When to Use Which

**Use `interface` when:**

- Defining the shape of an object or class contract.
- You need declaration merging (library authors, augmenting global types).
- Extending other interfaces in an OOP-style hierarchy.

**Use `type` when:**

- Defining unions, intersections, tuples, or mapped types.
- Aliasing primitives or function signatures.
- You want to prevent accidental re-declaration (safer for app code).
- Using advanced type features (conditional types, template literals, etc.).

```ts title="ApiResponse.ts"
// ✅ interface — object shape, extendable contract
interface ApiResponse {
  status: number;
  data: unknown;
}
```

```ts title="index.ts"
// ✅ type — union, can't be done with interface
type Result<T> = { ok: true; value: T } | { ok: false; error: string };

// ✅ type — function alias
type Predicate<T> = (value: T) => boolean;
```

**Style guide varies:** TypeScript's own handbook offers `interface` as the default heuristic for object shapes, switching to `type` only when a feature specific to type aliases is needed. Many community style guides prefer `type` everywhere for consistency. Both are valid for most object shapes — follow your team's style guide.
